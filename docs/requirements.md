# Специфікація вимог до програмного забезпечення (SRS) — версія v1.0

## 1. Межі версії v1.0 (Scope)

Продукт **ServiceCenter** призначений для централізованого ведення обліку заявок на ремонт споживчої електроніки, відстеження життєвого циклу обслуговування пристрою та збереження історії виконаних робіт.

### Що входить до v1.0 (In Scope):
- **Реєстрація нового замовлення:** внесення та збереження відомостей про клієнта та пристрій (бренд, модель, серійний номер, опис несправності), призначення відповідального сервісного інженера.
- **Картка замовлення:** інтерфейс вибору майстра, послідовної зміни статусу заявки та додавання переліку виконаних робіт і використаних запчастин.
- **Автоматичний підрахунок вартості:** обчислення підсумкової суми замовлення та відображення електронної квитанції на екрані.
- **Перелік замовлень:** виведення списку ремонтів у вигляді таблиці з фільтрацією за статусом («Прийнято», «В роботі», «Готово», «Видано») та пошуком за номером замовлення.
- **Збереження даних:** фіксація даних замовлень та історії зміни статусів у реляційній базі даних SQLite.

### Що не входить до v1.0 (Out of Scope):
- автоматичні SMS/Telegram-сповіщення клієнта про зміну статусу ремонту;
- сканування штрихкодів або маркування пристроїв;
- інтеграція зі складським обліком деталей та автосписання залишків;
- інтеграція з програмними РРО / банківським еквайрингом для онлайн-оплати;
- особистий кабінет клієнта для самостійного відстеження ремонту онлайн.

## 2. Функціональні вимоги (FR)

| ID | Вимога | Критерій приймання (Acceptance Criterion) |
| :--- | :--- | :--- |
| **FR-01** | Система повинна дозволяти Менеджеру-приймальнику зареєструвати нове замовлення, вказавши дані клієнта (ПІБ, телефон), параметри пристрою (бренд, модель, серійний номер) та опис несправності. | **AC-01:** Якщо обов'язкові поля заповнені, створюється замовлення з унікальним номером, початковим статусом «Прийнято» (`Accepted`), нульовою вартістю та записом в історії статусів. |
| **FR-02** | Система повинна перевіряти відсутність дубліката активного замовлення для вказаного серійного номера пристрою та дозволяти призначити Сервісного інженера на замовлення. | **AC-02:** Спроба створити друге незавершене замовлення на той самий серійний номер відхиляється з повідомленням; при виборі інженера він закріплюється за карткою замовлення. |
| **FR-03** | Система повинна дозволяти Сервісному інженеру додавати до замовлення в стані «В роботі» результат діагностики та позиції виконаних робіт/деталей (назва, кількість, ціна) з автоматичним перерахунком підсумкової суми. | **AC-03:** Підсумкова вартість (`TotalCost`) автоматично дорівнює сумі вартості всіх доданих позицій; введення кількості <= 0 або ціни < 0 відхиляється системою. |
| **FR-04** | Система повинна забезпечувати послідовну зміну статусів замовлення за життєвим циклом («Прийнято» -> «В роботі» -> «Готово» -> «Видано») із фіксацією часу кожної зміни в історії статусів та блокуванням редагування після видачі. | **AC-04:** Перехід із порушенням послідовності (наприклад, із «Прийнято» одразу у «Видано») або спроба змінити перелік робіт у статусі «Видано» блокується системою. |
| **FR-05** | Система повинна формувати електронну квитанцію замовлення та дозволяти користувачам здійснювати пошук за номером замовлення і фільтрацію таблиці за статусом («Прийнято», «В роботі», «Готово», «Видано»). | **AC-05:** За вибраним статусом або введеним номером відображаються відповідні замовлення; у картці замовлення формується підсумкова електронна квитанція з даними пристрою, майстра, робіт і фінальної суми. |

## 3. Нефункціональні вимоги (NFR)

| ID | Характеристика якості | Вимога | Критерій приймання |
| :--- | :--- | :--- | :--- |
| **NFR-01** | Продуктивність (Час відгуку) | Пошук замовлення за номером, фільтрація за статусом та збереження змін у картці замовлення повинні виконуватися не довше ніж за 2 с. | **AC-06:** У навчальному середовищі 95% запитів на пошук, створення та оновлення замовлення завершуються за час <= 2000 мс. |
| **NFR-02** | Надійність і цілісність даних | Система повинна запобігати збереженню некоректних або неповних даних без аварійного завершення роботи застосунку. | **AC-07:** 100% спроб зберегти порожні обов'язкові поля, від'ємну вартість або порушити послідовність статусів повертають зрозуміле повідомлення про помилку без пошкодження даних у БД SQLite. |
