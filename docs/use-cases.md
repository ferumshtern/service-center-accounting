# Специфікації варіантів використання (Use Cases) — v1.0

## Перелік варіантів використання v1.0
- **UC-01:** Зареєструвати замовлення та призначити майстра *(індивідуальна деталізація: Лавренюк Серафим)*
- **UC-02:** Зафіксувати результати ремонту та розрахувати вартість *(індивідуальна деталізація: Головань Євгенія)*
- **UC-03:** Сформувати квитанцію та закрити замовлення («Видано»)
- **UC-04:** Знайти та відфільтрувати замовлення за номером або статусом

## Детальна специфікація UC-01 (Виконавець: Лавренюк Серафим)

| Поле | Опис |
| :--- | :--- |
| **ID і назва** | **UC-01 «Зареєструвати замовлення та призначити майстра»** |
| **Мета** | Зареєструвати клієнта й пристрій, створити нову заявку на ремонт зі статусом «Прийнято» та закріпити відповідального сервісного інженера. |
| **Основний актор** | Менеджер-приймальник |
| **Тригер** | Клієнт звертається до сервісного центру та передає пристрій на діагностику або ремонт. |
| **Передумови** | Менеджер-приймальник відкрив форму реєстрації нового замовлення; у системі наявний довідник сервісних інженерів. |
| **Основний успішний сценарій** | 1. Менеджер-приймальник вводить дані клієнта (ПІБ, контактний телефон).<br>2. Менеджер-приймальник вводить відомості про пристрій (бренд, модель, серійний номер) та опис несправності.<br>3. Менеджер-приймальник обирає відповідального Сервісного інженера зі списку та підтверджує створення замовлення.<br>4. Система перевіряє, що всі обов'язкові поля заповнені коректно.<br>5. Система перевіряє, що для цього серійного номера немає іншого незавершеного замовлення (у статусах «Прийнято», «В роботі» або «Готово»).<br>6. Система створює замовлення, присвоює йому унікальний номер, початковий статус «Прийнято» (`Accepted`), записує подію в історію статусів і зберігає дані в БД.<br>7. Система відображає картку створеного замовлення з номером квитанції. |
| **Альтернативні / виняткові потоки** | **A1. Не заповнені обов'язкові поля клієнта або пристрою (на кроці 4):**<br>4а. Система не зберігає замовлення та виводить повідомлення із зазначенням пропущених полів.<br><br>**A2. Пристрій із таким серійним номером вже має активне замовлення (на кроці 5):**<br>5а. Система блокує дублювання квитанції та інформує менеджера про номер існуючого активного замовлення. |
| **Постумови** | **Успіх:** Замовлення збережено у статусі «Прийнято», призначено майстра, створено перший запис в історії статусів.<br>**Помилка:** Нове замовлення не створюється, база даних не змінюється. |
| **Пов'язані вимоги** | FR-01, FR-02, NFR-01, NFR-02 |
| **Критерії приймання** | AC-01, AC-02, AC-06, AC-07 |

## Детальна специфікація UC-02 (Виконавець: Головань Євгенія)

| Поле | Опис |
| :--- | :--- |
| **ID і назва** | **UC-02 «Зафіксувати результати ремонту та розрахувати вартість»** |
| **Мета** | Перевести замовлення у статус «В роботі», внести висновок діагностики, перелік виконаних робіт/запчастин, автоматично розрахувати вартість і перевести замовлення у статус «Готово». |
| **Основний актор** | Сервісний інженер |
| **Тригер** | Сервісний інженер розпочинає або завершує роботу над призначеним йому пристроєм. |
| **Передумови** | Замовлення зареєстроване в системі та перебуває у статусі «Прийнято» або «В роботі». |
| **Основний успішний сценарій** | 1. Сервісний інженер відкриває картку призначеного замовлення.<br>2. Якщо замовлення мало статус «Прийнято», інженер змінює його на «В роботі» (`InProgress`), а система фіксує перехід в історії статусів.<br>3. Інженер записує технічний висновок діагностики.<br>4. Інженер додає до картки замовлення позиції виконаних робіт та використаних деталей (назва, кількість, ціна за одиницю).<br>5. Система перевіряє допустимість редагування (замовлення не в статусі «Видано») та коректність числових значень (кількість > 0, ціна >= 0).<br>6. Система автоматично обчислює підсумкову вартість замовлення (`TotalCost`).<br>7. Інженер змінює статус замовлення на «Готово» (`Ready`), система фіксує зміну в історії статусів та зберігає оновлене замовлення. |
| **Альтернативні / виняткові потоки** | **A1. Спроба внести зміни у вже закрите замовлення зі статусом «Видано» (на кроці 5):**<br>5а. Система відхиляє редагування та повідомляє, що замовлення вже видано клієнту.<br><br>**A2. Введено некоректну кількість або від'ємну ціну деталі/роботи (на кроці 5):**<br>5б. Система не додає позицію та виводить попередження про некоректні числові дані.<br><br>**A3. Потрібні додаткові деталі — ремонт ще триває (альтернатива на кроці 7):**<br>7а. Інженер зберігає додані роботи, залишаючи замовлення у статусі «В роботі» без переходу у «Готово». |
| **Постумови** | **Успіх:** У картці замовлення збережено перелік робіт, автоматично розраховано `TotalCost`, статус оновлено на «Готово» із записом в історії статусів.<br>**Помилка:** Попередні дані та статус замовлення залишаються незмінними. |
| **Пов'язані вимоги** | FR-03, FR-04, NFR-01, NFR-02 |
| **Критерії приймання** | AC-03, AC-04, AC-06, AC-07 |
